Implementation Plan Review: 1-implement-initial-pwm-class.md

I have reviewed the implementation plan against the specification and existing codebase. The plan is solid, technically sound, and well-structured, but I have identified a specific divergence regarding the safety constraints for frequency changes and a suggestion for the testing workflow.

## 1. Spec Alignment
*   **Generally Strong**: The plan correctly adopts Approach 1 (Centralized Controller), covers the required fail-safe behaviors, and properly limits scope (no internal loop).
*   **Divergence on Frequency Safety**: The spec explicitly requires that "Frequency changes at runtime... are permitted **only if the caller explicitly opts in per-channel**." The plan currently proposes allowing the change with just a warning log ("allow frequency change but emit a warning log"). Given the known 0% duty glitch inherent to the sysfs backend, this opt-in constraint is a safety mechanism that should be enforced, not just logged.

## 2. Implementation Approach
*   **Good Hardware Abstraction**: Using `ChannelConfig` and the existing `rpi_hardware_pwm` library is the correct path.
*   **Effective Locking**: The strategy to snapshot `_pending` state under lock and then release the lock before performing blocking sysfs I/O is excellent for maintaining responsiveness in the command interface.
*   **Fail-Safe**: The approach to catch exceptions per-channel during `fail_safe()` ensures that a failure in one channel doesn't prevent others from being stopped.

## 3. Testing Strategy
*   **Incremental Testing**: The plan lists `sw/tests/test_pwm_controller.py` as a deliverable only in **Phase 5**. However, the "Test Plan" sections for Phases 1-4 imply that tests will be run to verify each step.
*   **Recommendation**: To ensure the "Defend" step of the Builder workflow is effective, the test file should be initialized in Phase 1 and incrementally expanded in each phase, rather than writing the entire suite at the end.
