## Specification Review: Raspberry Pi 5 HardwarePWM BLDC Multi-Motor Control Class

### Overall Assessment

This is a well-structured spec with clear problem framing, good safety awareness, and honest tracking of open questions. However, there are several significant feasibility concerns that stem from a gap between what the spec demands and what the underlying `rpi_hardware_pwm` library can actually deliver.

---

### 1. Feasibility — Critical Concerns

**The 1000 Hz control loop vs. sysfs file I/O**

The spec requires a control loop rate of ≥1000 Hz (line 33). The installed `HardwarePWM` library (which the spec references as the mandatory backend) operates via the Linux sysfs interface — it literally opens files under `/sys/class/pwm/` and writes text into them on every parameter change. Each `change_duty_cycle` call does a file open, write, and close. Each `change_frequency` call does **three** file I/O operations (zero duty, write period, restore duty).

For 4 motors at 1000 Hz, that's potentially 4,000–12,000 file I/O syscalls per second through sysfs. This is not a memory-mapped register write — it goes through the VFS layer. Achieving stable 1 ms cycle times with this I/O pattern on a Linux userspace Python process is questionable and should be validated before committing to this target.

**Recommendation**: The spec should either (a) qualify the 1000 Hz target as aspirational pending benchmarking, or (b) acknowledge that the sysfs backend may need to be replaced with a direct `/dev/mem` or kernel-module approach for true 1 kHz+ rates.

**"Synchronized" updates are not truly atomic**

The spec requires "synchronized update operation applies new PWM values across all active motors within one control tick" (line 46). But `HardwarePWM` writes to each channel sequentially via sysfs. There is no hardware mechanism on the Pi to atomically latch multiple PWM channels simultaneously. The best you can do is "fast sequential writes" which will always have some skew.

The spec should define what "synchronized" actually means in measurable terms — e.g., "all channel updates complete within X microseconds of each other" rather than implying true hardware-level atomicity.

**`change_frequency` is destructive**

Looking at the library (lines 148-163), `change_frequency()` must first zero the duty cycle, write the new period, then restore the duty cycle. This means every frequency change causes a momentary output glitch (duty goes to 0 briefly). If motors have independent frequencies that change at runtime, this is a safety concern that the spec doesn't address.

### 2. Hardware Channel Limitation

The `HardwarePWM` library supports channels 0-3 (line 45-46 of the library). However, the standard Raspberry Pi PWM hardware only has **2 independent PWM generators** (PWM0 and PWM1) — channels 2 and 3 on the Pi 5 may share timing hardware with 0 and 1. The spec says "multiple BLDC motor drivers" but doesn't define how many. This is listed as an open question (line 109), which is good, but it's marked as "Critical (Blocks Progress)" while the spec is moving forward anyway.

**Recommendation**: At minimum, state the expected channel count (even as a range like "2-4 motors") so the design can be evaluated.

### 3. Python + Real-Time + GIL

The spec acknowledges the GIL concern (line 60) and suggests "avoiding the GIL for timing-critical paths." In practice, CPython's GIL means you cannot get deterministic sub-millisecond timing from a Python thread. The spec should be more explicit about the expected approach:

- Will the control loop run in a separate **process** (via `multiprocessing`)?
- Will it use `ctypes`/C extension for the timing-critical inner loop?
- Or is the expectation that Python's `threading` is "good enough" given the sysfs bottleneck?

This is a design decision that materially affects the class API and should be at least directionally resolved in the spec.

### 4. Completeness — Good but Missing Some Details

**What's well-covered:**
- Problem/desired state clearly articulated
- Safety/fail-safe requirements present
- Input validation requirements present
- Thread-safety requirement resolved via amendment
- Two solution approaches compared honestly
- Risk table is realistic

**What's missing or underspecified:**

- **No chosen approach**: The spec presents two approaches but doesn't select one. A builder needs to know which to implement.
- **Safe state definition**: The spec says "drives all managed motors to a safe state" but doesn't define what that state is. Duty cycle 0? PWM disabled? Both? This matters for BLDC drivers where "disabled" vs "0% duty" may produce different motor behaviors (coast vs brake).
- **Startup/shutdown sequence**: Listed as an open question (line 114) but is important enough to warrant at least a preliminary answer. A robot arm with gravity-loaded joints needs careful arming.
- **Partial failure behavior**: What happens when one channel update fails during a synchronized commit (line 113)? This is also an open question but is critical for safety.
- **Error reporting model**: How does the caller learn that an update was rejected or a fault occurred? Exceptions? Callbacks? Return codes? This affects the API contract.
- **Control loop ownership**: Does this class own and run the control loop, or does an external scheduler call an `update()` method each tick? This is a fundamental architectural question left unanswered.

### 5. Clarity

The spec is well-written and terminology is consistent. The amendments section showing iterative refinement is helpful. One ambiguity:

- "Control loop rate of at least 1000 Hz" — is this the spec's minimum acceptable threshold, or a target? If the measured rate on real hardware is 800 Hz, does that fail the spec?

### 6. Testing Strategy

The test scenarios (lines 133-142) are reasonable but would benefit from:
- Specifying whether tests run on real hardware, a mock/stub, or both
- Defining the "required max jitter threshold" referenced in non-functional test 1 (it's circular — the spec says test against a threshold but doesn't define the threshold)

### 7. Minor Notes

- The spec notes itself (line 172) that no parent SPIR exists, which means the TICK protocol's precondition isn't satisfied. This is flagged honestly, which is good.
- Amendment numbering is reversed (Amendment 2 before Amendment 1) — presumably intentional for reverse-chronological display per TICK protocol.
