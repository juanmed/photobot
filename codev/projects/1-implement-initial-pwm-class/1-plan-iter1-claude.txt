This is a reasonable scoping decision (the spec's open question marked it as multi-threaded/multi-process, and the plan explicitly calls it out of scope), so this is a minor observation, not a blocker.

### 2. Technical Approach

**Sound overall.** A few specific callouts:

**a) `sw/` is not a Python package.** There is no `__init__.py` in `sw/`. The test mock fixture uses `monkeypatch.setattr('sw.pwm_controller.HardwarePWM', ...)` — this import path won't resolve unless `sw/` becomes a package or the import is done differently. The plan should note that an `__init__.py` needs to be created (or the monkeypatch path adjusted).

**b) Python version mismatch.** The plan says "Python 3.8+" in Resource Requirements, but `pyproject.toml` specifies `requires-python = ">=3.12"`. This isn't a functional problem (3.12 > 3.8), but the plan should match the project's actual minimum. This also means `statistics.quantiles` (3.8+) is fine, but there's no need to worry about 3.8 compatibility — you can freely use 3.12 features like `@dataclass(slots=True)`.

**c) numpy is already a project dependency** (listed in `pyproject.toml`), so the Phase 3 risk about numpy not being present is a non-issue. You can just use it.

**d) Lock design in Phase 4 is well-considered.** The snapshot-then-release pattern for `update()` is the right call — avoids holding the lock across sysfs I/O. Good.

**e) `fail_safe()` vs `stop()` semantics.** Phase 2 says `fail_safe()` calls `pwm.stop()` on each instance, and the risk section acknowledges `stop()` might tear down the sysfs entry. This is a real concern — if `fail_safe()` destroys the HardwarePWM instances, you can't recover without re-calling `start()`. The plan identifies this risk but doesn't commit to a decision. **Recommendation**: Decide now. Given the spec says fail-safe = "duty=0 then disable," `fail_safe()` should only call `change_duty_cycle(0)` (and possibly mark channels as disabled internally). Reserve `pwm.stop()` for the final `stop()` cleanup. This avoids the ambiguity.

**One structural concern**: Phase 5 (Test Suite) is the final phase, but Phases 1–4 each describe their own acceptance criteria and test plans. **Are builders expected to write tests inline during each phase, or defer all testing to Phase 5?** This is ambiguous. If tests are deferred to Phase 5, then Phases 1–4 can't be independently validated (their acceptance criteria can't be checked). If tests are written per-phase, Phase 5 becomes a consolidation/gap-fill phase. **The plan should be explicit about this.** I'd recommend writing tests per-phase and using Phase 5 for coverage gap analysis and thread-safety stress tests only.
